# Переоценка товаров через сервис объектов — дизайн

Дата: 2026-11-10. Статус: утвержден пользователем.
Источник требований: ТЗ `tz-repricing.md` (курс AICourse, task07).

## Зачем

Менеджер магазина раз в сезон меняет цены части ассортимента на процент с даты. Сейчас — вручную,
с ошибками округления, а повторное проведение удваивает изменение. Нужен один запрос к сервису
объектов, который переоценивает товары, а повторный запрос с той же датой результат не меняет.

## Цели

- Маршрут `POST …/prices/reprice` сервиса объектов (корень `objects`).
- Расчет новой цены: старая × (1 + процент / 100), до целых рублей, половина — вверх.
- Идемпотентность по дате: запись на тот же период и товар заменяет прежнюю.
- Каждое правило таблицы ТЗ подтверждено тестом YAxUnit, написанным до кода (Red → Green, отдельные коммиты).

## Не цели (из ТЗ, «Вне рамок»)

Несколько цен товара внутри дня; цены, записанные позже даты переоценки (остаются); товары дешевле
1 рубля как отдельный случай; виды цен, валюты, НДС, отмена переоценки; публикация и проверка в браузере.

## Решения пользователя

| Вопрос | Решение |
|---|---|
| На каком сервисе строим | Текущий `Extensions/Bills` (расширение `СчетаМагазина`), не стартовый набор |
| Новое расширение или существующее | Правки вносим в существующее расширение Bills, новое не создаем. Исключение из правил 1 и 7 `agents.md` — шаблон URL и одна функция-обработчик в HTTP-сервисе |
| Проверочные тесты подключения | Удалить только падающий `Сложение_Падает`; `Сложение_Проходит` остается «тестом до задачи» |
| Цена 0 | Не «нет цены»: переоценивается (`oldPrice: 0`, `newPrice: 0`), в регистр пишется 0 |
| Предложения по текстам ошибок и краевым случаям (ниже) | Утверждены |

## Подходы

Рассмотрены:
1. **Маршрут в существующем HTTP-сервисе Bills + новый общий модуль** — выбран: единственный способ
   получить маршрут сервиса объектов `objects`.
2. Новое расширение со своим HTTP-сервисом — отвергнут: расширение не может заимствовать HTTP-сервис
   другого расширения, а второй сервис с корнем `objects` невозможен; с другим корнем это не маршрут
   сервиса объектов. Кроме того, пользователь запретил новое расширение.
3. Стартовый набор задания вместо Bills — отвергнут пользователем.

## Устройство

### Расширение `СчетаМагазина` (`Extensions/Bills`)

- **HTTP-сервис `СчетаМагазина`**: новый шаблон URL `Переоценка` = `/prices/reprice`, метод POST,
  обработчик `Переоценить`. В модуль сервиса добавляется только:
  ```bsl
  Функция Переоценить(Запрос)
  	Возврат СчетаМагазинаПереоценка.Переоценить(Запрос);
  КонецФункции
  ```
- **Новый общий модуль `СчетаМагазинаПереоценка`** (Сервер = да, Глобальный и ВызовСервера = нет):
  - `НоваяЦена(СтараяЦена, Процент) Экспорт` — без обращения к базе:
    `Окр(СтараяЦена * (1 + Процент / 100), 0, РежимОкругления.Окр15как20)`.
  - `Переоценить(Запрос) Экспорт` — возвращает `HTTPСервисОтвет`:
    1. Разбор тела и проверка входа, все ошибки собираются сразу. Есть ошибки → `400`, ничего не читается
       и не пишется.
    2. Срез последних `РегистрСведений._ДемоЦеныНоменклатуры` на `КонецДня(Дата - 1)` (конец дня,
       предшествующего дате переоценки) по товарам запроса.
    3. Товар без записи в срезе → `skipped` с `reason: "no_price"`.
    4. Остальным — запись `НоваяЦена` с периодом `НачалоДня(Дата)` в одной транзакции; набор записей
       с отбором `Период`, `Номенклатура` заменяет прежнюю запись → повторный запрос дает ту же цену.
    5. Ответ `200`: `{"repriced": [{"id","oldPrice","newPrice"}], "skipped": [{"id","reason"}]}`,
       порядок — как в `items`.
  - Собственная функция ответа JSON: `ОтветJSON` модуля сервиса не экспортная, а модуль сервиса
    сверх одной функции не меняем (правило 1). Для пути ошибки используется существующий экспортный
    `СчетаМагазинаДанные.Ошибка`, для разбора идентификатора — `СчетаМагазинаДанные.УникальныйИдентификаторИзСтроки`.

### Идентификатор товара

Как отдает сервис Bills: строка UUID, 36 символов, нижний регистр (`Строка(Ссылка.УникальныйИдентификатор())`).

### Проверка входа и тексты (утверждены)

Ответ при ошибке: `400`,
`{"error": {"code": "invalid_data", "message": "Неверные данные переоценки", "details": [{"path", "message"}]}}`.

| Случай | path | message |
|---|---|---|
| Тело не JSON или не объект | `null` | `Тело запроса должно быть JSON-объектом` |
| `items` нет, не массив или пустой | `items` | `Список товаров должен быть непустым массивом` |
| Элемент не строка UUID | `items[i]` | `Неверный идентификатор товара` |
| Товар не найден | `items[i]` | `Товар не найден` |
| Товар помечен на удаление | `items[i]` | `Товар помечен на удаление` |
| Элемент — группа справочника | `items[i]` | `Это группа, а не товар` |
| Повтор (второе и следующие вхождения) | `items[i]` | `Товар повторяется` |
| `percent` нет или не число | `percent` | `Процент должен быть числом: допустимо от -50 до 100, кроме 0` |
| `percent` вне [-50; 100] или 0 | `percent` | `Процент <значение> недопустим: допустимо от -50 до 100, кроме 0` |
| `date` нет, не `ГГГГ-ММ-ДД` или несуществующая дата | `date` | `Дата должна быть в формате ГГГГ-ММ-ДД` |

`<значение>` — число через точку, без разделителей разрядов (`Формат(Процент, "ЧРД=.; ЧГ=0; ЧН=0")`).
Оговорка: 1С читает число из JSON как число, поэтому `150.50` выводится как `150.5`.

Прочее:
- Права — обычные права пользователя, без привилегированного режима.
- Сбой записи (не ошибка входа) — откат транзакции, `500 internal_error`, как в остальном сервисе Bills.

## Тесты (расширение `Тесты`)

| Правило | Уровень | Модуль |
|---|---|---|
| Процент вверх | юнит | `ТестыЮнит` (тег `Юнит`) |
| Процент вниз с округлением до рубля | юнит | `ТестыЮнит` |
| Половина рубля — вверх | юнит | `ТестыЮнит` |
| Новая цена с начала дня, старая в истории осталась | интеграция | `ТестыИнтеграция` (тег `Интеграция`) |
| Товар без цены пропущен с `no_price` | интеграция | `ТестыИнтеграция` |
| Повторный запрос с той же датой не меняет цену | интеграция | `ТестыИнтеграция` |
| Неверный процент — `400`, в регистре ничего | интеграция | `ТестыИнтеграция` |

- Интеграционные тесты вызывают `СчетаМагазинаПереоценка.Переоценить` с заглушкой HTTP-запроса YAxUnit,
  без публикации; модуль с `.УдалениеТестовыхДанных()`, без `.ВТранзакции()` (код сам открывает транзакцию).
- Товары и исходные цены тесты создают сами, даты — в прошлом, чтобы автоматическая запись цены 0
  на текущую дату (модуль объекта `_ДемоНоменклатура`, `ПриЗаписи`) была позже даты переоценки и не
  влияла на срез.
- Записи регистра, созданные конфигурацией при записи товара и проверяемым кодом, регистрируются
  к удалению (`ЮТест.Данные().ДобавитьКУдалению`, ключи записи) до утверждений — чтобы удалялись
  и после красного прогона.
- Из `ТестыПроверкаПодключения` удаляется `Сложение_Падает`.
- Конфиги: `tests/yaxunit/юнит.json`, `интеграция.json`, `все.json` (пути — с обратным слешем).
- Red и Green — отдельными коммитами; тест, прошедший с первого прогона, помечается в плане охранным.

## Приемка (из ТЗ)

- Отчет jUnit общего конфига: все тесты таблицы + `Сложение_Проходит`, код результата 0.
- В `git log` у каждого не охранного правила коммит падающего теста раньше коммита поведения.
- Файл `.http` с двумя примерами.
- После полного прогона в регистре цен нет записей тестов, в том числе со ссылкой на удаленный тестовый товар.
