## Правила

### 1. Существующие модули не меняем
Все доработки делаем только в новых модулях. Уже существующие модули не правим: ни в основной конфигурации, ни в существующих расширениях (в том числе `Extensions/Bills`). Если нужно изменить поведение, используйте новый модуль, подписку на событие или перехватчик метода (`cfe-borrow`, `cfe-patch-method`) в новом расширении.

**Согласованное исключение (2026-11-10, переоценка товаров):** новые маршруты сервиса объектов добавляем
в существующий HTTP-сервис `СчетаМагазина` расширения Bills — шаблон URL в `HTTPServices/СчетаМагазина.xml`
и однострочная функция-обработчик в его модуле, которая только передает запрос в новый общий модуль.
Иначе нельзя: обработчики HTTP-сервиса живут только в его модуле, а заимствовать HTTP-сервис другого
расширения нельзя. Существующие функции модуля сервиса не меняем. См.
`docs/superpowers/specs/2026-11-10-repricing-design.md`.

### 2. Код пишем по принципам SOLID, DRY и KISS
- **SOLID** — у модуля одна ответственность; зависимости от абстракций (общие модули с понятным API), а не от деталей.
- **DRY** — без дублирования: общую логику выносим в общий модуль, сначала ищем готовое в БСП.
- **KISS** — самое простое работающее решение, без лишних уровней абстракции.
- Соблюдаем стандарты разработки 1С: https://its.1c.ru/db/v8std

### 3. Внешние источники указываем всегда
Если используем информацию из интернета (документация, статьи, ИТС, форумы, репозитории), указываем ссылку на источник в ответе, а при переносе решения в код — в комментарии рядом с ним:

```bsl
// Источник: https://its.1c.ru/db/v8std/content/456/hdoc
```

### 4. Перед написанием кода прогоняем ТЗ через навыки superpowers
Порядок: `brainstorming` → `writing-plans` → `test-driven-development` → `executing-plans` / `subagent-driven-development` → `verification-before-completion` → `requesting-code-review` → `finishing-a-development-branch`. Отладка — через `systematic-debugging`.

### 5. Все доработки — через git
- Если репозиторий не создан, создаем его (`git init`).
- В `.gitignore` добавляем все содержимое папки `Config` — ее не должно быть в публичном репозитории:

  ```gitignore
  /Config/
  ```
- Также не коммитим временные файлы веб-публикации: `ws/**/logs/`, `ws/**/tmp/`.
- Каждая доработка — отдельная ветка и осмысленные коммиты.

### 6. Информационная база
Конфигурация связана с файловой информационной базой `File="C:\Users\psi\Downloads\AICourse\DBIS07";`. Пользователь: `Администратор`, пароль пустой.

### 7. Вся разработка ведется в новых расширениях конфигурации
Каждое расширение складывается (выгружается в XML) в каталог `Extensions\<ИмяРасширения>`.
Исключение: доработки сервиса объектов ведутся в существующем расширении `СчетаМагазина`
(`Extensions\Bills`), новое расширение для них не создаем — решение пользователя от 2026-11-10 (см. правило 1).
- Новое расширение создаем через `cfe-init`, проверяем через `cfe-validate`.
- Задаем расширению собственный префикс имен (`NamePrefix`) и используем его для всех новых объектов.
- После изменений загружаем расширение в ИБ (`db-load-xml`/`db-cfe-admin`) и выгружаем обратно в `Extensions\<ИмяРасширения>`, чтобы git и база не расходились.

### 8. Основную конфигурацию не меняем
Каталог `Config/` и конфигурацию в ИБ не редактируем и в ИБ не загружаем. Объекты основной конфигурации нужны только как источник для заимствования в расширения.

### 9. Доработки в расширениях тестируем через YaxUnit
- Тесты живут в отдельном расширении `Тесты` (`Extensions\Тесты`, префикс `Тесты`), а не в рабочих расширениях.
- Подключение, написание и запуск тестов — через навык `testing-with-yaxunit` (адаптированная копия в репозитории: `.claude/skills/testing-with-yaxunit/SKILL.md`, раздел «Под своё окружение»), отчет — в формате jUnit.
- Сначала тест (red), потом код (green), см. `test-driven-development`.
- YaxUnit: https://github.com/bia-technologies/yaxunit

| Что | Значение |
|---|---|

| Движок | `vendor\yaxunit\YAxUnit-25.12.cfe`, расширение `YAXUNIT`, релиз https://github.com/bia-technologies/yaxunit/releases/tag/25.12, sha256 `805a2277c997a3c24be0b0d080696479e91e4a15ed7e27aaf3991a7346522d70`. Файл не правим и в XML не выгружаем |
| Расширение тестов | `Extensions\Тесты`; модули — общие, `Сервер` = да, `Глобальный` и `ВызовСервера` = нет |
| Конфиги запуска | `tests\yaxunit\*.json` (`все.json` — все тесты расширения `Тесты`) |
| Отчеты и логи | `.logs\` (в git не входит), отчет — `.logs\yaxunit\все.xml`, код — `.logs\yaxunit\все-exit.txt` |

Прогон одной командой (загрузка расширения `Тесты` → снятие безопасного режима → запуск → итог):

```powershell
powershell -NoProfile -File tools\run-tests.ps1            # с загрузкой расширения
powershell -NoProfile -File tools\run-tests.ps1 -SkipLoad  # только прогон
```

Код выхода: `0` — все прошли, `1` — есть падения, `2` — отчет не сформирован. Сверять число тестов в отчете
с числом зарегистрированных: модуль с ошибкой компиляции YAxUnit молча пропускает.

#### Подводные камни (проверено)

- **Безопасный режим.** Конфигуратор подключает загруженное расширение в безопасном режиме, а в нем YAxUnit
  падает с ошибкой «Чтение конфигурационного файла недоступно». После каждой загрузки `YAXUNIT`/`Тесты`
  снимаем безопасный режим обработкой `tools\epf\СнятиеБезопасногоРежимаРасширений`
  (собрать навыком `epf-build` в `.logs\СнятиеБезопасногоРежимаРасширений.epf`; `run-tests.ps1` запускает ее сам).
  COM-коннектор `V85.COMConnector` в системе зарегистрирован с ошибкой (`TYPE_E_LIBNOTREGISTERED`) — не использовать.
- **Пути в JSON — только с обратным слешем** (`"C:\\Users\\..."`). Путь `C:/Users/...` YAxUnit считает
  относительным (`ЮТПараметрыЗапускаСлужебный.ЭтоАбсолютныйПутьWindows`), и отчет, код и лог молча
  уходят мимо — клиент закрывается без единого файла.
- **Команды 1С запускать из PowerShell**, а не из Git Bash: Bash переписывает аргументы вида `/F...`.
- `/UpdateDBCfg -Extension` вместе с `/LoadCfg` в одной команде дает «Ошибка в параметрах командной строки» —
  загрузку и обновление выполнять отдельными вызовами.
- Перед загрузкой закрыть клиенты 1С этой базы.

### 10. В метаданных используем `е`, а не `ё`
В именах, синонимах и комментариях метаданных пишем `е`, а не `ё` (например, `Отчет`, `Расчет`, `Счет`, а не `Отчёт`, `Расчёт`, `Счёт`). Это же относится к новому коду и комментариям в модулях.
